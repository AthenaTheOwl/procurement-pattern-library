# Test a transfer before learning its outcome

Method update: October 18, 2026. Proposed experiments below are not reported as executed results.

The library records whether a procurement pattern transferred into an AI application. A completed story can make almost any resemblance look inevitable. A stronger application record states the expected mechanism, the context where it may fail and an observable disconfirming result before the outcome is known.

For dual sourcing, distinguish having a fallback named in a registry from keeping it usable. A synthetic prospective application can require the fallback to process a held-out case within a declared time and disclosure budget. If failover meets availability but violates the quality threshold, record the friction rather than relabeling the objective after the fact.

Use this protocol when a human authors the next pattern application; this refresh does not generate new canonical pattern files. Link a public upstream decision or reproducible run in `upstream_artifact`. State the expected mechanism, failure context, disconfirming result and planned observation window in the optional front-matter fields `expected_mechanism`, `failure_context`, `disconfirming_result` and `observation_window_days` from `schemas/case.schema.json`, and expand on them in the case body. Existing cases without these fields stay valid. The window is capped at ninety days by the outcome rule (DEC-PPL-001); leave `outcome` empty until measured. The retrospective should report missing follow-up separately from failed transfer, along with denominators. A useful pattern names where the analogy breaks as clearly as where it holds.
